# LuzLunar

**LuzLunar** ("moonlight" in Spanish) is a personal fork of [moonlight-stream/moonlight-qt](https://github.com/moonlight-stream/moonlight-qt) for an Apple Silicon Mac streaming from [Apollo](https://github.com/anyosag/Apollo). It's macOS-only and needs Qt 6.8 or later (`app/fork/fork.pri` stops qmake on older Qt). Its look changes aren't gated per platform, so other platforms would get them too, untested.

It ships as `LuzLunar.app`, but keeps Moonlight's bundle ID (`com.moonlight-stream.Moonlight`) and settings domain, so paired PCs and settings carry over from the official app. Upstream code and upstream strings still say "Moonlight"; only the app bundle, the display name and the fork's own UI use LuzLunar.

## Builds

- `.github/workflows/fork-macos.yml` builds an arm64-only `LuzLunar.app` and DMG with `scripts/fork/build-mac.sh`. The script renames the bundle after `macdeployqt`. The workflow runs on pushes to `master` and `claude/**` and on pull requests. It takes its runner, Qt version and aqtinstall pin from upstream's `build-win-mac.yml`. It also uploads `scripts/fork/trackpad-probe.mm`, built, as `LuzLunar-trackpad-probe-…`.
- Signing: with the `LUZLUNAR_SIGNING_P12` secret (a base64 `.p12` holding a self-signed code-signing certificate) and `LUZLUNAR_SIGNING_P12_PASSWORD`, CI imports the certificate into a temporary keychain and the script signs with it (`LUZLUNAR_SIGN_IDENTITY`, its SHA-1, and `LUZLUNAR_SIGN_KEYCHAIN`). macOS ties privacy permissions to the signature, and an ad-hoc one changes with every build, so only certificate-signed builds keep the Accessibility permission trackpad passthrough uses. Without the secret (pull requests from other repositories, say) the build is ad-hoc signed and warns. `sync-upstream.yml` passes the secrets on. Hardened runtime stays off: without a Team ID it makes library validation reject the bundled Qt frameworks.
  - Making the certificate, once (keep `signing.p12` backed up offline; a new certificate means granting Accessibility again):
    ```sh
    openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=LuzLunar Code Signing" \
      -addext "keyUsage=critical,digitalSignature" -addext "extendedKeyUsage=critical,codeSigning" \
      -addext "basicConstraints=critical,CA:false" -keyout key.pem -out cert.pem
    openssl pkcs12 -export -legacy -inkey key.pem -in cert.pem -name "LuzLunar Code Signing" -out signing.p12
    base64 -i signing.p12 | gh secret set LUZLUNAR_SIGNING_P12 -R anyosag/LuzLunar
    gh secret set LUZLUNAR_SIGNING_P12_PASSWORD -R anyosag/LuzLunar
    ```
  - Locally, import `signing.p12` into the login keychain and set `LUZLUNAR_SIGN_IDENTITY` to the SHA-1 `security find-identity -p codesigning` lists for it.
- Locally, run `bash scripts/fork/build-mac.sh Release` from the repo root (paths with spaces are fine). It needs Qt's tools on `PATH`; with Homebrew that's `qtbase`, `qtdeclarative`, `qtsvg` and `qtimageformats`, the last for the WebP the native spinner uses. Two optional switches, both off in CI:
  - `LUZLUNAR_SKIP_DMG=1` skips the DMG, so `create-dmg` isn't needed.
  - `LUZLUNAR_INSTALL=1` quits LuzLunar, moves `/Applications/LuzLunar.app` to the Trash and installs the new build. It then refreshes LaunchServices (`lsregister -f`), which caches an app's Info.plist by bundle ID.
- The script edits the bundle's Info.plist after `macdeployqt`: the LuzLunar names, the build ID, and no Game Mode (see Fork features). It fails the build if the Game Mode opt-out didn't take.
- Every build has a build ID: the version plus the commit, like `6.2.0-fork.ee5b3ba`, the same as in the artifact and DMG names. It's shown at the bottom of Settings › Keyboard & Clipboard (`ForkPreferences.buildId`, from qmake's `FORK_BUILD_ID`) and is the bundle's `CFBundleVersion`, so Finder's Get Info tells copies apart.
- Upstream's `build.yml` (every platform) is disabled in this repo's Actions settings. The file stays unchanged so upstream merges stay clean.
- `.github/workflows/sync-upstream.yml` merges upstream `master` daily onto the `upstream-sync` branch and opens (or updates) a pull request into `master`, so upstream changes are looked over before they ship. It builds the app from the merge. Merge that pull request with "Create a merge commit". Opening it needs "Allow GitHub Actions to create and approve pull requests" in the repository's Actions settings. To sync upstream workflow changes, it needs a `SYNC_TOKEN` secret: a fine-grained token for this repo with Contents, Workflows and Pull requests read/write; pull requests opened with it also run the usual checks.
- The prebuilt dependencies `setup-deps.py` and `setup-deps.ps1` download are checked against SHA-256 hashes kept in those scripts. Add the new hashes when changing their `TAG`.
- Actions are pinned to commits; Dependabot proposes updates.
- A push to `master` is also published as an over-the-air update: the `publish` job makes a signed GitHub release with the environment `release`'s `FORK_UPDATE_KEY` (see Fork features, Updates).

## Installing a build

Once a build with Updates is installed, later master builds arrive through Settings › Updates; these steps are for the first one, and for branch builds.


1. Download the `LuzLunar-macOS-arm64-…` artifact from the workflow run, then unzip it and open the DMG.
2. Drag LuzLunar to Applications and delete the official `Moonlight.app`. Both share a bundle ID and settings, so keep only one. Paired PCs and settings carry over. Also delete older LuzLunar copies outside Applications (an unzipped artifact folder, a mounted DMG), or Spotlight and Launchpad may open one of them; the build ID in Settings shows which build is running.
3. The app isn't notarized (and is ad-hoc signed without the signing secret). Open it the first time with right-click → Open, or run `xattr -dr com.apple.quarantine /Applications/LuzLunar.app`.
4. For trackpad passthrough, allow LuzLunar once in System Settings › Privacy & Security › Accessibility (Settings › Mouse & trackpad has a button). Certificate-signed updates keep the permission. After an ad-hoc build, or the first certificate-signed one, macOS may show LuzLunar as allowed but ignore it: remove it from the list with − and add it again.

### Patches to submodules

Fixes to code the fork doesn't own (`moonlight-common-c`) live in `patches/<name>/*.patch`. `scripts/fork/apply-patches.sh` applies them, and `build-mac.sh` runs it after `setup-deps.py`; a plain `qmake`/`make` build doesn't, so run it first. A patch that no longer applies fails the build, so a submodule update can't drop a fix silently; one that's already applied only warns (drop it once upstream has it). To change one, edit the submodule, then `git -C <submodule> diff > patches/<name>/NNNN-name.patch` and `git -C <submodule> checkout .`.

- `moonlight-common-c/0001`: the RTSP parser read past the end of a message whose last option has no line break after it. Upstream rewrote the parser (moonlight-common-c aeba988); drop this patch when the submodule moves past it.
- `moonlight-common-c/0002`: the control stream's disconnect intercept, which runs before ENet checks a datagram, took a disconnect from anyone; it now checks the peer and session IDs as ENet does. That's hardening, not a fix for deliberate attacks: the session ID is 2 bits, so a sender who can reach the control port needs at most 4 tries, as with ENet's own check.
- `moonlight-common-c/0003`: a feature, not a fix, kept for good: `LiSendForkInputPacket()` queues an input packet the caller built (header and payload, 8 to 128 bytes) on a control channel, reliably or not, through the same queue and encryption as every input event. Trackpad passthrough's frames use it. The library has no other way to send a packet it doesn't know.

## Fork features

- **Look** (the redesign; `app/gui/Fork*.qml`):
  - **Theme**: `ForkThemeData.qml` is the `ForkTheme` singleton (registered in `forkqml.cpp`): the "Night" palette in dark mode and "Day" in light mode, following the system appearance, with Moonlight gold as the accent. Text is the system font (SF Pro) and numbers are SF Mono (Menlo where it's missing). The window is opaque: the native title bar and toolbar sit on the toolbar color (`windowchrome_mac.mm`).
  - **Stock controls** use the `Fusion` style with a palette from `ForkTheme` (main.qml), so upstream's dialogs, menus, check boxes and fields match too; dialogs get `ForkDialogBackground`, a themed title and `ForkButton`s, and menus and lists `ForkPopupBackground`. Effects (shadows, rounded box art) only draw where the renderer supports them, so offscreen screenshots still show the panels and the art.
  - **Sizes and motion** follow the design: 44 pt controls, 20 pt card corners, 22 pt card padding, content at most 1152 wide and centered. Looping or moving animations stop when the system's Reduce Motion is on (`ForkTheme.reduceMotion`, from `ForkWindowChrome`).
  - **Feedback**: `ForkToast` confirms actions at the bottom of the window (`window.forkToast()`); Help shows the shortcuts while streaming (`ForkShortcutsDialog`).
  - **Shared controls**, all on `QtQuick.Templates`: `ForkButton` (primary, strong, accent, default, quiet, danger, link), `ForkSwitch` and `ForkSwitchRow`, `ForkSegmented`, `ForkOptionCard` (an option drawn as a card, or a compact radio row), `ForkCard`, `ForkSlider`, `ForkTextField`, `ForkText` (the type styles), `ForkSymbol` (a tinted SF Symbol), `ForkKeys` and `ForkTip` (keycaps), `ForkWarnBox`, `ForkNavButton` and `ForkMoonMark` (the brand mark, drawn with `QtQuick.Shapes`).
  - **Your PCs** (`PcView`): a card per PC (`ForkHostCard`) whose screen is a moon scene for its state (`ForkStatusScene`: ready, streaming, waking, asleep, offline, checking, not paired, needs a newer host; still with Reduce Motion), its status and the action that fits (Show apps, Pair with this PC, Wake PC, Details); the title and discovery status above (`ForkPcHeader`); an Add a PC card and a This Mac line below (`ForkPcFooter`, `ForkThisMacStrip`).
  - **Apps** (`AppView`): the running app's banner with Resume and Quit (`ForkAppsHeader`), and tiles with rounded box art, the name and chips (own stream settings, direct launch, hidden) under it.
  - **Starting a stream** (`StreamSegue`): `ForkLaunchPanel` shows the moon mark (its reflection ripples once the session is initialized), the app and PC, five steps (Find PC, Handshake, Video, Audio, Input) that complete as moonlight-common-c's 11 connection stages do, with upstream's stage line, the stream's size, frame rate, bitrate and codec with the app's profile applied (`AppView.forkStreamSummary()`), and the shortcuts to end the stream and free the pointer.
  - **Settings** (`ForkSettingsView`): a sidebar of sections, each its own file loaded when picked: Display (`ForkSettingsDisplay`: aspect ratio cards, resolution, frame rate, bitrate, HDR, display mode, Fit or Stretch with a diagram, V-Sync, frame pacing), Video, Audio, Mouse & trackpad, Keyboard & Clipboard, Gamepads, Host & network, App and This Mac. It replaces upstream's `SettingsView` and binds the same `StreamingPreferences` and `ForkPreferences` with upstream's side effects (bitrate follows the size, frame rate and YUV 4:4:4 unless set by hand; the bitrate limit clamps; mDNS restarts polling; the language retranslates). Upstream's touchscreen trackpad option is left out (Macs have no touchscreen).
  - **Screenshots**: the harness (`screenshotharness.cpp`) also shows a PC's apps, the launch panel, every Settings section and an app's stream settings (on Global, Office, Custom, scrolled to the end, and in the window's default 600 pt height). Native AppKit calls (`ForkWindowChrome::attach()`, `MacIntegration::windowNumber()`) skip non-Cocoa windows, so it can run with `QT_QPA_PLATFORM=offscreen` (add `QT_QUICK_BACKEND=software` and `SDL_MAC_BACKGROUND_APP=1`).
- **Mac keyboard remapping** (`app/fork/forkkeymap.*`, `forkinput.*`, `forkpreferences.*`):
  - Command, Control and Option can each send Ctrl, Alt, the Windows key or nothing. The defaults are Command → Ctrl, Control → Windows and Option → Alt.
  - Moonlight's Ctrl+Option+Shift shortcuts still match the physical keys.
  - While streaming with Command remapped, Cmd+Q/Cmd+H go to the host (`app/fork/mac/macintegration.mm`).
  - Settings live under `fork/keyTargets` in Moonlight's preferences.
  - Unit tests are in `tests/fork/keymap_test.cpp`.
- **Mac shortcuts while streaming** (`app/fork/forkmacshortcuts.*`, `forksystemshortcuts.*`, `mac/macintegration.mm`, `app/gui/ForkSettingsKeyboard.qml`, `ForkMacShortcutsOption.qml`):
  - Upstream's "Capture system keyboard shortcuts" uses SDL's keyboard grab, which on macOS turns off every system shortcut (`CGSSetGlobalHotKeyOperatingMode`), screenshots included. LuzLunar instead takes only the groups checked under it in Settings and sends them to the host: Spotlight, Mission Control, Spaces, window shortcuts, keyboard navigation, input sources, Emoji/Look Up/Dock/Help and the Game Overlay by default. The app switcher (⌘Tab), Globe key shortcuts, screenshots (⇧⌘3/4/5) and Visual Intelligence stay with the Mac unless checked. "Send every Mac shortcut to the PC" brings back upstream's grab.
  - In Settings they're in Keyboard & Clipboard (`ForkSettingsKeyboard`), under "Send system shortcuts to the PC": a switch per group, "Send every Mac shortcut to the PC" and the Control-Option-Shift-K tip, bound to the same `ForkPreferences` as `ForkMacShortcutsOption`, which is hooked into the old `SettingsView` and no longer shown.
  - Capture defaults to "in fullscreen" (upstream: off). A one-time startup step (`fork/captureSysKeysDefaulted`) sets `capturesyskeys` once, so it also changed existing settings.
  - The shortcuts are macOS's symbolic hot keys, turned off with private SkyLight calls looked up with `dlsym`: `CGSSetSymbolicHotKeyEnabledForConnection` only for LuzLunar's own windows, which macOS drops when LuzLunar exits. ⌘Tab can't be set per app, so it uses `CGSSetSymbolicHotKeyEnabled` for every app, with a crash record (`fork/heldMacShortcuts`, "pid:1,2") written before it's turned off. A later LuzLunar turns those back on at startup unless that copy is still running.
  - They're taken while upstream would grab (its mode, fullscreen and capture rules) and the stream window has focus, and given back on focus loss, Ctrl+Option+Shift+K, leaving fullscreen and stream end. Hot keys already off in System Settings are left alone. Ids are checked by name before use (`SLSSymbolicHotKeyName`), so a renumbered one is skipped. Force Quit, logout, accessibility and brightness keys are never taken.
  - macOS's screenshot tools (⇧⌘4's crosshair, ⇧⌘5's toolbar) need the cursor, which a fullscreen stream holds still for the host (relative mouse mode). While ⌘⇧ are held and for a second after, the stream looks every 100 ms for the `screencapture` process's full-screen window (window owners are readable without the screen recording permission), lets the cursor go while it's up, and takes it back when it closes.
  - `scripts/fork/hotkey-probe.mm` lists the hot keys with their names and tests the calls; re-run it after a macOS update. If the calls disappear, nothing is taken and the Mac keeps its shortcuts. If ⌘Tab stays off after a crash, open LuzLunar again, or toggle it in System Settings › Keyboard › Keyboard Shortcuts, or log out.
  - Unit tests are in `tests/fork/macshortcuts_test.cpp`.
- **No Game Mode** (`scripts/fork/build-mac.sh`): upstream's Info.plist opts into macOS Game Mode (the games category, `LSSupportsGameMode` and `GCSupportsGameMode`, ae1c6580), so fullscreen streams turned it on. - **Trackpad passthrough** (`app/fork/forktrackpad.*`, `forktrackpadpassthrough.*`, `forkmultitouch.*`, `forktrackpadgestures.*`, `luztouchpad.h`, `mac/trackpadcapture_mac.*`, `mac/gesturesuppressor_mac.*`, `app/gui/ForkSettingsMouse.qml`):
  - With anyosag/Apollo on Windows 11, the Mac trackpad's fingers go to the PC, which feeds them to a synthetic Windows touchpad. Two modes, in Settings › Mouse & trackpad › Trackpad (`trackpadMode`, saved as `trackpadmode`), and each app's Stream Settings can choose otherwise:
    - **Mac trackpad** (`TM_MAC_TRACKPAD`, the default): macOS makes the pointer motion, clicks (tap to click, Force Touch, secondary click) and scrolling with its momentum, with its own tracking speed, palm rejection and timing, so the trackpad feels as it does on the Mac. They go to Windows as a mouse; only the fingers of a three- or four-finger gesture or a pinch go to the touchpad, which Apollo makes gesture-only (it never moves the pointer or clicks). Windows' pointer acceleration is off while it streams (Apollo's FORK.md), so it doesn't add to macOS's.
    - **Windows touchpad** (`TM_WINDOWS_TOUCHPAD`): every finger goes to the touchpad, and Windows makes its own pointer, taps, scrolling with inertia, pinch and gestures, with its touchpad settings.
    - **Mac mouse** (`TM_MAC_MOUSE`): off; the trackpad is a mouse as in Moonlight.
    - The old on/off setting (`trackpadpassthrough`) becomes Mac trackpad when it was on, Mac mouse when it was off; a new install starts on Mac trackpad. A profile's old `trackpadPassthrough` reads the same way (`StreamProfiles::profile()`). The app's chips and the launch panel show "Mac trackpad" or "Touchpad".
  - Either mode captures the pointer: such a stream uses the Games pointer mode even if the app's profile says Remote desktop (`StreamProfiles::createSession()`), so the hidden Mac cursor can't leave the window and click on the Mac.
  - It runs while the mode is one of the two, the host offers it (feature flag `0x40000000`), the stream has the mouse in relative mode, and the stream window is the key window of the active app; it stops on focus loss, when the mouse is freed (⌃⌥⇧Z, the screenshot tools) and when the stream ends. A host without it gets a message beside the notch, and the trackpad stays a mouse. Mac trackpad also needs the host to offer `0x20000000`: LuzLunar asks for it with `luzTrackpad=mac` at launch (`ForkLaunchArgs`, before the flags are known), and with an older Apollo it says so and uses the Windows touchpad.
  - Capture (`mac/trackpadcapture_mac.mm`): a local monitor on AppKit's touch events reads every touch in the stream window (SDL drops trackpad touches). The view asks for resting touches (`wantsRestingTouches`), so a thumb or palm macOS calls resting arrives as such instead of as a lift and a new touch. `ForkTrackpad::ContactTracker` (pure C++) gives up to 5 fingers slots 0-4; a finger already down when passthrough starts, a sixth finger, a Magic Mouse and the touches palm rejection keeps out are left out, and a finger macOS takes away or calls resting is cancelled, so Windows doesn't tap. Each change is a frame of every finger still down, sent with patch `0003` on the touch channel: reliable unless only moving, and repeated every 100 ms while fingers are down.
  - **Palm rejection** (`ContactTracker`, `forkmultitouch.*`), after macOS's own rules and other drivers' (libinput, Windows' touchpad requirements):
    - A new touch waits until it's decided, at most 3 frames or 50 ms, and then goes to Windows from where it is by then; a quick tap decided as it lifts goes down and up. The decision sticks until it lifts.
    - Contact sizes come from Apple's private MultitouchSupport framework (loaded at run time; `NSTouch` has no size), as gesture apps read them: each contact's ellipse and the hand part Apple's driver gave it (fingerID 1 thumb, 2-5 fingers, 6-7 palm). Each `NSTouch` gets the nearest contact within 0.06 of the pad. A palm is fingerID 6-7, or a short axis of 10 mm or more in 2 of its first 3 frames (fingertips stay under about 9.4 mm, palms over about 9.8); a finger that spreads to that for 2 frames in a row later is cancelled once and left out until it lifts. If the framework is missing or its contacts stop making sense, the log says why and it goes on without sizes.
    - macOS's resting touches wait for as long as they rest. A touch that lands within 200 ms of a first key, or 500 ms of the last while keys keep coming, is left out (modifiers and Command, Control or Option shortcuts don't count, so Command-click works). A thumb (fingerID 1) that lands in the bottom 15% of the pad and moves less than 2 mm while another finger moves is a resting thumb.
    - The log has the stream's counts when it ends: `Palm rejection this stream: … palms, … touches while typing, … resting thumbs, … late palms cancelled`.
  - **Mac trackpad mode** (`ForkTrackpadPassthrough`, `ForkTrackpad::Carry`, `MacMute`): a second local monitor reads macOS's own pointer motion (`deltaX`/`deltaY`, fractional points after macOS's acceleration) and precise scrolling (`scrollingDeltaX`/`Y` with its momentum phases) before SDL rounds them.
    - Pointer: points become the stream's pixels so the pointer crosses as much of the video as it would of the Mac's screen (the video's size in the window, the fit absolute mouse mode uses), with what's left of a pixel carried to the next move, and goes out with `LiSendMouseMoveEvent`. SDL's copy of the motion is dropped (any SDL motion within 100 ms of one sent).
    - Scrolling: a point is a wheel unit (120 a notch) times the scroll speed (Settings › Mouse & trackpad › Trackpad › Scroll speed, `fork/trackpadScrollSpeed`, 0.25-3, default 1), carried the same way, already in the Mac's scrolling direction ("Reverse mouse scrolling direction" applies), with `LiSendHighResScrollEvent`/`HScrollEvent`; SDL doesn't get it. A mouse wheel's lines stay SDL's.
    - Gestures: fingers are followed and palm-rejected as in the other mode, but Windows hears of them only once 3 are down or macOS starts a pinch (a magnify event), and then until the last one lifts. Meanwhile macOS's pointer motion, scrolling and clicks are dropped.
    - What it doesn't do like a Mac: rubber-band overscroll and two-finger swipe back/forward (Windows apps only do those for touchpad input), and Force Click / Look Up.
  - The frame (`luztouchpad.h`) is shared byte for byte with anyosag/Apollo (`src/fork/luztouchpad.h`), and `tests/fork/luztouchpad_test.cpp` runs in both repos' CI. Keep the copies identical.
  - Muting in Windows touchpad mode (`ForkTrackpad::MuteFilter`): SDL gives every Mac mouse event the same mouse id, so the trackpad's own pointer motion, scrolling and clicks are told apart by time: those from 5 ms before a finger lands to 150 ms after the last lifts, and scrolling that keeps coming after that (momentum), are dropped. A click with a finger down presses the pad in the frames; a click just after a lift is macOS's tap to click, dropped since Windows taps itself. An external mouse used within 150 ms of the trackpad is muted too.
  - macOS's gestures (`mac/gesturesuppressor_mac.mm`): while passthrough runs, an event tap drops the Dock's gesture events (CGEventType 30: Spaces and fullscreen swipes, Mission Control, App Exposé, Show Desktop and Apps pinches), deciding each gesture whole at its first event (`ForkTrackpadGestures::DockGestureFilter`). It needs Privacy & Security › Accessibility (a message says so once per stream otherwise). Notification Center's edge swipe and three-finger drag aren't Dock events, so with "Also pause Notification Center's swipe and three-finger drag" (`fork/trackpadPauseMacSettings`, on) they're switched off through System Settings' private `MTTGestureBackEnd` (with its iCloud sync off for the change) while it runs, and back on 2 s after it stops (sooner at stream end), only where the value is still what LuzLunar wrote. A crash record (`fork/trackpadHeldSettings`, "pid:edge=3/0,drag=1/0") is written first, and the next LuzLunar puts them back unless that copy still runs. Without the class, only the tap holds gestures back.
  - Recovery: if a gesture stays off, open LuzLunar again or set it in System Settings › Trackpad › More Gestures (Notification Center) and › Accessibility › Pointer Control › Trackpad Options (three-finger drag).
  - `scripts/fork/trackpad-probe.mm` checks what this relies on: `touches` logs AppKit's trackpad touches (resting ones asked for, or not with `--no-resting`), `mt` pairs them with MultitouchSupport's contacts and prints hand parts and axes, with the widest finger and narrowest palm at the end (to set palm rejection's 10 mm from your own hand), `pointer` logs macOS's pointer deltas, precise scrolling with its phases, and pinches (move at one speed with the tracking speed low, then high: the deltas should follow it), `tap` logs the Dock's gesture events and their fields (`--drop` drops them like LuzLunar), `mtt list|get|set` exercises `MTTGestureBackEnd`. Re-run it after a macOS update.
  - Debugging: `LUZLUNAR_TRACKPAD_LOG=1` logs every frame; `LUZLUNAR_TRACKPAD_FORCE=1` sends frames to a host that doesn't offer passthrough (it drops them) and uses Mac trackpad mode without the host's flag.
  - Unit tests are in `tests/fork/trackpad_test.cpp` (touches to frames, palm rejection, Mac trackpad mode's gestures, carrying and muting, the other mode's muting, when it runs), `tests/fork/multitouch_test.cpp` (pairing touches with MultitouchSupport's contacts) and `tests/fork/trackpadgestures_test.cpp` (the Dock filter, the settings hold and its crash record).
- **Updates** (`app/fork/forkupdater.*`, `forkupdaterules.*`, `forkhostupdates.*`, `updatekey.h`, `mac/selfupdate_mac.*`, `app/gui/ForkSettingsUpdates.qml`):
  - Every master build that passes CI is an update, for LuzLunar and for anyosag/Apollo alike. Branch and pull request builds never are. Settings › Updates shows both.
  - Publishing: `fork-macos.yml`'s `publish` job, on a push to master only, turns the build into a GitHub release `luzlunar-b<run>`, marked latest, with `LuzLunar-macOS-arm64.zip` (the signed app, zipped with `ditto` by `build-mac.sh`), the DMG, `update.json` and `update.json.sig`. The manifest is `{product: "luzlunar", channel: "master", run, version, commit, published, notes, asset: {name, url, sha256, size}}`; the signature is the base64 Ed25519 signature over its exact bytes, made with `openssl pkeyutl -sign -rawin`. The job also checks it against the public key in `updatekey.h`, and keeps the newest 15 releases. Apollo's `build-windows.yml` does the same with `apollo-b<run>`.
  - Keys: the private key is the `FORK_UPDATE_KEY` secret of each repo's `release` environment, whose deployment rule allows only `master`, so branch builds can't sign. The public key is compiled into `app/fork/updatekey.h` and Apollo's `src/fork/update_key.h`. Back the key up offline; a new one needs a new public key in both apps and one manual install on each machine. Making it, once:
    ```sh
    openssl genpkey -algorithm ed25519 -out update-signing-key.pem
    openssl pkey -in update-signing-key.pem -pubout -outform DER | tail -c 32 | xxd -i
    gh secret set FORK_UPDATE_KEY --env release -R anyosag/LuzLunar < update-signing-key.pem
    ```
  - Ordering: CI builds carry `FORK_BUILD_RUN` (the workflow's run number) and `FORK_BUILD_CHANNEL` (`master` only for a push to master), through `build-mac.sh` and `fork.pri`. A release is an update when its run is higher, or whatever runs isn't a master build. Automatic installs only replace a master build, so a branch build installed on purpose stays until you click Install.
  - LuzLunar (`ForkUpdater`, started by main.qml, never by command-line runs): it checks 20 s after opening and every 30 minutes. It reads `releases/latest/download/update.json` and `.sig`, following redirects only over HTTPS to github.com and `*.githubusercontent.com`. It checks the signature, then the manifest, and downloads the zip to `~/Library/Caches/…/updates/<run>/`, checking its size and SHA-256. It unpacks it with `ditto`, and accepts the app only if its code signature meets this app's designated requirement (`mac/selfupdate_mac.mm`): the same certificate and bundle ID, which is also what keeps Accessibility. An ad-hoc build can't pass that, so it says to install the next build by hand once.
  - Installing: the toolbar's update button (it was upstream's, pointing at Moonlight's site) opens Settings › Updates, whose "Install and restart" starts a detached helper script (`swap.sh` in the updates folder) and quits. The helper waits for LuzLunar to exit, checks the new build runs (`--version`), moves the current bundle to `updates/previous/`, moves the new one in, runs `lsregister -f` and opens it. If the new build doesn't write `updates/started` within 30 s, it puts the previous one back. With "Install LuzLunar updates automatically" (`fork/autoUpdate`, off), it installs when you quit, or restarts quietly into the update (`open -g`) after 10 minutes in the background with no stream. Never during a stream.
  - The helper leaves `updates/result` ("installed <run>", "rolledback <run>", "failed quit|move|check"), which the next LuzLunar shows once as a toast and in Settings; its log is `updates/update.log`. "failed move" usually means macOS's App Management protection stopped it: allow LuzLunar in Privacy & Security › App Management (Settings › Updates has a button), then install again.
  - Apollo PCs (`ForkHostUpdates`): every 30 minutes and when Settings › Updates opens, each paired, online Apollo PC is asked `GET /actions/update` with the paired client certificate (`ApolloClient`). Its "Update Apollo now", the PC menu's "Update Apollo", and its automatic switch `POST` `{"action":"install"}` or `{"automatic":true|false}`. Apollo then does the work itself, as SYSTEM, without a UAC prompt, and only with builds its own key check accepts. LuzLunar shows "updating" while the PC restarts, then the new version or Apollo's rollback message. It needs the PC's "Update Apollo" permission; clients that had every permission get it. 401 means this Mac lacks it, and 404 means an Apollo from before updates.
  - Unit tests: `tests/fork/updaterules_test.cpp` (manifests, ordering, addresses, the helper's result, base64 and Ed25519 against a throwaway key).
- **Apollo clipboard sync** (`app/fork/clipboardsync.*`, `apolloclient.*`, `clipbundle.*`, `clipfiles.*`, `mac/pasteboard*`):
  - With LuzLunar's Apollo build (anyosag/Apollo), the clipboard travels as a *clipbundle* through `GET`/`POST /actions/clipboard?type=bundle&v=1`, using the paired client certificate. One bundle carries plain text, RTF, HTML, PNG/JPEG and Office's drawing format (`Art::GVML ClipFormat` on Windows, `com.microsoft.Art--GVML-ClipFormat` on the Mac), so formatting survives Word, Excel and PowerPoint copies between the Mac and the PC. Other Apollo versions answer 400, and sync falls back to plain text (`type=text`).
  - `clipbundle.*` is shared byte for byte with anyosag/Apollo (`src/fork/clipbundle.*`), and `tests/fork/clipbundle_test.cpp` runs in both repos' CI. Keep the copies identical. It has the compact little-endian format, zlib compression for text formats, a content hash, the Windows "HTML Format" header, and the send rules:
    - a file copy sends its files' list (below) and its text (the names), never an image
    - an image is sent only for picture copies (no text, or an image offered first), so an Excel range doesn't send a rendered bitmap
    - Word's HTML that points at local image files is dropped when RTF (which embeds the pictures) is there
    - bundles are limited to 64 MB, and a compressed item can't claim more than deflate's 1032:1
    - received images are written only if their bytes start with their type's PNG or JPEG signature
  - Only what changed is transferred. The PC returns a state token (its clipboard sequence number) and a content hash, and the Mac sends them back, so an unchanged clipboard costs a few bytes. Uploads are skipped while `NSPasteboard.changeCount` and the content hash are unchanged. This state lasts for the app's life, per host.
  - On the Mac, the pasteboard is read and written on the sync worker thread (`mac/pasteboard_mac.mm`), so streaming never waits for Office to render or for TIFF/HEIC to convert (with ImageIO). Images go as PNG, HEIC photos as JPEG.
  - Modes are Off, Shortcuts only (Ctrl+Option+Shift+U sends, G fetches) and Automatic. Automatic sends the clipboard when a stream starts or regains focus, and fetches the PC's when it loses focus or ends. New installs start with Shortcuts only; installs that already had hosts when this default changed keep Automatic, the earlier default.
  - Responses from the host are capped (64 MB for bundles, 32 MB otherwise).
  - Requests run one at a time on a worker thread and report back through an SDL event, because the Qt event loop is paused while streaming.
  - Sync never wipes the local clipboard with an empty one and never sends back content that came from the host. Password-manager clips (`org.nspasteboard.ConcealedType`/`TransientType`, or Windows' `ExcludeClipboardContentFromMonitorProcessing`) are never synced automatically, and when sent with the shortcut they're marked private on the other side. Logs show types and sizes, never content.
  - The host must be Apollo, and Apollo must give this device its Clipboard permissions. Sync checks this through serverinfo `<Permission>`.
  - **Files** (`clipfiles.*`): files and folders copied in Finder or Explorer cross over and paste as copies. It needs "Copy files too" (Settings › Keyboard & Clipboard, `ForkPreferences.clipboardFiles`, on by default), an Apollo whose serverinfo has `<LuzClipboardFiles>1</LuzClipboardFiles>`, and Apollo's File Upload and File Download permissions for this device.
    - The bundle carries a `files/manifest` item (`clipbundle.h`, "File copies"): a transfer id made from the entries, then each entry's relative path, size, modification time and whether it's a folder. The contents follow in chunks of up to 8 MB, a request each: `GET /actions/clipboard?type=file&transfer=…&index=…&offset=…` from the PC, `POST` to it, then `POST type=files-done`, which puts them on the PC's clipboard. Fetches ask for files with `files=1`. The other side's clipboard changes only once every file has arrived.
    - From the PC, files land in `~/Library/Caches/<app>/Clipboard Files/<transfer>/` (`<transfer>.partial` until they're all there), and the pasteboard gets their file URLs, as Finder's copy does. The cache keeps the last 3 copies for a day, and unfinished ones go when the next stream starts. A copy that's still whole in the cache isn't fetched again.
    - Limits: 10,000 entries and 20 GB per copy, and automatic sync moves at most 1 GB (a toast says to use the shortcut). The Mac needs the copy's size plus 512 MB free.
    - Folders are walked in name order. Symlinks inside them, `.DS_Store` and `._*` files are left out. Names Windows can't have are changed the same way on both sides (`clipbundle::local_paths()`), and an entry whose name is taken already, ignoring case, is left out with what's inside it.
    - Progress shows in the toast and as a percentage on the Dock icon, which can be seen while the stream is in the background. What an automatic fetch says (it starts as the stream goes to the background) waits until the stream is back in front.
    - A file that changes while it's being sent stops the copy. Copies stop when the stream ends, and the fetch as a stream ends leaves files out. A copy that failed isn't tried again on its own; the shortcuts do.
    - Not covered: files that aren't on disk (Outlook attachments, files inside a zip), the PC's mapped network drives (Apollo runs as SYSTEM), cut and paste, and resuming a broken copy.
    - Unit tests: `tests/fork/clipfiles_test.cpp`, the manifest in `tests/fork/clipbundle_test.cpp`, and file URLs on a private pasteboard in `tests/fork/pasteboard_test.mm`.
  - Messages ("Clipboard sent to the PC", errors) appear beside the notch while the notch bar is on screen, and in Moonlight's status overlay otherwise.
- **This Mac as a drive on the PC** (`app/fork/macdrive.*`, `macdriverules.*`, `mac/macdrivesetup*`, `app/gui/ForkMacDriveCard.qml`):
  - With anyosag/Apollo, a stream over the LAN can give the PC this Mac's disk as a network drive: File Explorer shows it as `M:` (or another free letter) under this Mac's name, until a minute after the stream ends (Apollo's FORK.md, "Mac drive for LuzLunar"). Streams over a VPN or the internet never ask.
  - It's macOS's own File Sharing (SMB). It's set up once, in Settings › This Mac › "This Mac on the PC":
    - turn on "Show this Mac's disk on the PC" (`fork/macDrive`, off by default);
    - turn on File Sharing in System Settings › General › Sharing (the card's button opens it), and under its ⓘ › Options…, Windows File Sharing for this account: macOS keeps the hash Windows' NTLM sign-in needs only then;
    - save the account's password. LuzLunar checks that it opens the account (`-[ODRecord verifyPassword:error:]`) and keeps it in the login keychain (a generic password, service "LuzLunar Mac drive"), never in its settings.
  - The card says what's still missing, and looks again every 2 s while it's shown:
    - File Sharing off (nothing answers on 127.0.0.1:445);
    - Windows File Sharing off for the account: its `AuthenticationAuthority` lists no `SMB-NT` hash. That's a hint, since the record's format isn't documented;
    - no share of the whole disk, for a standard account;
    - no password;
    - and what the last LAN stream got (`fork/macDriveLast`).
  - The whole disk:
    - File Sharing's share of the startup disk if there is one: a SharePoints record for `/` with SMB on, by its SMB name;
    - else, for an administrator, macOS's share of the startup volume, by its name (`Macintosh HD`);
    - then the home folder (the account's short name), which macOS shares with its own account;
    - Apollo maps the first that the Mac offers and the account may open, and when only the home folder works, the message says so.
  - When it asks:
    - `ForkNetworkLink`'s first probe of a stream says whether it goes over the LAN, by the notch bar's rule: Moonlight's `RI_LAN` check, else the PC being on-link, and never through a VPN.
    - Then, on a worker thread, it checks serverinfo's `<LuzMacDrive>` and the "Network Drive" permission (`0x00400000`). It reads the password from the keychain and checks it again, so a changed password is caught here, not on the PC. It checks that File Sharing answers.
    - Then it sends `POST /actions/drive` `{"action": "map", "shares", "user", "password", "name"}`, and a `GET` every 500 ms for up to 15 s until the drive is mapped or failed. Apollo takes the request's own address, so nothing tells it where the Mac is.
  - The password:
    - It leaves the Mac only in that request's body, over the paired TLS connection with its pinned certificate, and Apollo keeps it in memory only.
    - Logs show the PC, the shares and Apollo's answer, never the password.
    - The keychain item is tied to LuzLunar's signature, so a build signed with another certificate (or an ad-hoc build) asks once to be allowed to read it.
  - Messages beside the notch (or in the corner pill of a windowed stream):
    - "On the PC, this Mac is drive M:", or the same for the home folder;
    - each failure with what fixes it: Windows File Sharing for the account, the PC blocking NTLM, File Sharing unreachable, a connection to this Mac under another account, nobody signed in to Windows…;
    - nothing for a drive kept from an earlier stream;
    - without the notch bar they're only logged and shown in Settings.
  - Unit tests: `tests/fork/macdriverules_test.cpp` (the shares, when a stream asks, Apollo's answers) and `tests/fork/macdrivesetup_mac_test.mm` (the account, File Sharing, the shares and a keychain item of its own, on the CI Mac).
  - **Untested** on a real Mac and PC:
    - the shares macOS 26 offers Windows (an administrator's `Macintosh HD` in particular);
    - the System Settings link, whose id isn't documented;
    - the `SMB-NT` hint;
    - what macOS's privacy protections let File Sharing serve from Desktop, Documents and Downloads.
- **Notch info bar** (`app/fork/mac/notchbar.*`, `app/fork/streamstats.*`):
  - In fullscreen on a MacBook with a camera notch, the strip beside the notch shows the app and PC name on the left. On the right it shows the frame rate, network latency, bitrate, codec and loss.
  - **The connection** (`app/fork/forknetworklink.*`, `forklinkrules.*`, `mac/networklink*`): first on the right, which interface carries the stream and how fast: `Ethernet 1 Gb/s`, `Wi-Fi 5 GHz 866 Mb/s`, `Thunderbolt Bridge`, `VPN over Wi-Fi`.
    - It shows only on networks that have carried a LAN stream of this PC: while the stream goes over the LAN, or on a network where this PC was streamed over the LAN before, with `· not via LAN` when this stream isn't (through a VPN, say). Over the internet elsewhere it doesn't show.
    - Over the LAN means Moonlight's own check at stream start says so (`getActiveAddressReachability()` returns `RI_LAN`, the check that picks local streaming). When it couldn't tell, or a custom packet size skipped it, the PC's address being in the subnet of the interface carrying the stream decides. A VPN interface never counts.
    - A network is its router: macOS's `NetworkSignature` for the interface (router address and hardware address, from the dynamic store), or `Router` and `ARPResolvedHardwareAddress`. It's stored as a SHA-256 under `fork/lanNetworks/<PC uuid>`, the newest 32 per PC. A link with no router, like a cable straight to the PC, isn't remembered but shows while its stream is on the LAN.
    - The interface is the one a connected UDP socket to the PC's address picks, so nothing is sent. Its kind comes from `SCNetworkInterface` (any wired adapter is Ethernet; `bridge0` is the Thunderbolt Bridge; `utun`, `ipsec`, `ppp` and similar are VPNs, over the primary interface), Ethernet speeds from `SIOCGIFMEDIA`, and Wi-Fi's band and rate from CoreWLAN, which macOS may hide without Location access; it then just says Wi-Fi. LuzLunar never asks for Location access.
    - It's probed on a thread of its own when the stream starts, which also logs it (`[fork] Stream link: …`), and every 5 seconds while the bar is up, so it follows a stream that moves to Wi-Fi when a cable is unplugged.
    - Unit tests: `tests/fork/forklinkrules_test.cpp` (the text, when it shows, the remembered networks) and `tests/fork/networklink_mac_test.mm` (routes, interfaces and speeds on the CI Mac).
  - macOS keeps a fullscreen window below the notch, so the bar is a separate non-activating panel above the stream's level that joins its fullscreen Space. It uses Liquid Glass (`NSGlassEffectView`) on macOS 26 and vibrancy before that.
  - Stats come from the decoder's once-a-second stats tick, computed only while the bar is listening.
  - The bar shows only while the stream is fullscreen on the active Space of a display with a notch. Turn it off in Settings › Keyboard & Clipboard.
  - A notched display has two shapes: the full panel, including the strip beside the notch (3024×1964, about 1.54:1, on a 14" MacBook Pro), and the area below the notch (3024×1890, 16:10). Fullscreen picks by the stream's aspect ratio, at any size (`ForkVideoScaling::useSpacesFullscreen()` in `app/fork/forkvideoscaling.*`, with the rule in `forkpolicy.*` and tests in `tests/fork/policy_test.cpp`):
    - The full panel's ratio (3024×1964, 1512×982…): a borderless window the size of the screen, video under the notch. The bar can't show, and the controller notices the window covers its screen and keeps the corner pill off it, so messages use Moonlight's red overlay.
    - The ratio below the notch (3024×1890, 2560×1600, 1920×1200…): a macOS fullscreen Space below the notch, with the bar.
    - Any other ratio (16:9, 21:9, 4:3…): a Space below the notch while the bar is on or Fullscreen fill is Stretch, because only a Space leaves the strip beside the notch for the bar, and a stretched picture must never be drawn under the notch; with both off, upstream's choice.
    - Upstream matched only the two exact native sizes. In Fullscreen mode every other size got the borderless window, which lacks the fullscreen style, so the bar never showed.
  - Messages appear in a third pill beside the notch. A red dot blinks twice, then grows into the pill; the app name fades out if they don't both fit. With Reduce Motion the pill just fades in and out.
    - Moonlight's poor connection warning ("Slow connection to PC · reduce your bitrate") stays until the connection recovers. It arrives on moonlight-common-c's receive thread through `ForkStreamStats::reportConnectionStatus()`, which tells `Session` whether the bar showed it.
    - Clipboard messages come through `ClipboardSync::setMessageSink()` and stay 3 seconds. One that arrives during the warning shows, then the warning returns.
    - While the stream is windowed, both appear in a pill in the window's bottom-left corner instead (`ForkCornerMessage`): the same glass capsule, icon and text, fading in as it rises 6 pt (only fading with Reduce Motion). It's a child window of the stream window, so it moves, resizes and changes Spaces with it, and clicks pass through it.
    - Fullscreen on a display without a notch, or with the bar turned off, they stay in Moonlight's red status overlay as before.
    - A warning that's up moves along: between the bar and the corner pill, into the overlay when neither is on screen, and back out when one returns. The connection status only arrives when it changes, so `ForkStreamStats` keeps the last one for `connectionPoor()` and `setConnectionWarningInOverlay()`.
  - The bar stays hidden while the stream window enters or leaves fullscreen. Once the panel's first fullscreen Space is gone (the stream went windowed), macOS keeps it on the desktop's Space, and ordering it in again doesn't move it. So when the shown panel isn't on the active Space, its pills move to a new panel, which joins the stream's Space.
- **Fullscreen stretch** (`app/fork/forkvideoscaling.*`, `app/gui/ForkStretchOption.qml`):
  - Apollo makes a virtual display at any size, so a stream's aspect ratio can differ from the screen's. Fullscreen fits it with black bars; "Fullscreen fill" in Settings › Basic Settings, under Display mode, can be set to Stretch to fill the screen instead, which distorts the picture. It's saved as `fullscreenstretch`, and each app can override it in "Stream Settings..." (Global, Fit or Stretch, profile key `fullscreenStretch`).
  - It only applies in fullscreen, both Fullscreen and Borderless windowed. A windowed stream always fits, and the setting is disabled while Display mode is Windowed.
  - `ForkVideoScaling::stretchActive()` is true while the session's preference is on and the stream window has an SDL fullscreen flag (`SDL_WINDOW_FULLSCREEN_DESKTOP` includes `SDL_WINDOW_FULLSCREEN`'s bit, so both kinds count). `ForkStreamExtensions` turns it on with the session's own copy of the settings, so app profiles count, and off when the stream ends. It's one atomic window pointer plus a flags read, because libplacebo's pacer thread and vt_metal's display-link thread call it. The rule is `ForkPolicy::stretchActive()`, tested in `tests/fork/policy_test.cpp`. Each change is logged as `[fork] Fullscreen stretch on` / `off`.
  - Every renderer and the mouse mapping get the stretch from `StreamUtils::scaleSourceToDestinationSurface()`, which returns early and leaves the destination as the whole surface. That covers libplacebo, vt_metal, the SDL renderer, and absolute mouse and touch, so clicks land on the stretched picture. The window sizing in `Session` also calls it, but only while the window isn't fullscreen. `vt_avsamplelayer` picks `AVLayerVideoGravityResize` when it's created (it's recreated when the window changes), and `vt_metal` adds the stretch state to the cache key of its video quad.
  - On a notched display a stretched stream stays below the notch: any ratio that isn't the full panel's goes into a Space, like with the notch bar. A stream with the full panel's ratio still fills the panel, since it has nothing to distort.
  - With Stretch chosen, Settings shows how far off the picture is on the first display, like "16:9 on this screen: 11% taller". On a notched display it measures against the area below the notch, except for a stream with the full panel's ratio, which fills the panel and shows no distortion.
- **This Mac** (`app/fork/clienthardware.*`, `app/fork/mac/clienthardware_mac.mm`, `app/fork/forkhwrules.*`):
  - `ClientHardware` (a QML singleton) knows the Mac LuzLunar runs on: the chip (`machdep.cpu.brand_string`), the Metal GPU (none in some CI VMs), the hardware decoders and the displays. Settings shows it in a "This Mac" group (`ForkThisMacGroupBox.qml`). It reads again on `refresh()` and whenever macOS reports changed screen parameters.
  - Decoders come from `VTIsHardwareDecodeSupported` for H.264, HEVC and AV1. HEVC Main10 has no API, so `hasHevcMain10()` copies the GPU rules of `VTBaseRenderer::checkDecoderCapabilities()` in `vt_base.mm`; keep the two in sync.
  - Displays come in `CGGetActiveDisplayList` order, the index `StreamUtils::getNativeDesktopMode()` takes. Its native and below-the-notch pixel sizes are used as they are, so they match the session's notch logic. AppKit adds the name, scale, notch (`safeAreaInsets.top > 0`), refresh rate (`maximumFramesPerSecond`, and the slowest from `maximumRefreshInterval`), HDR (EDR headroom above 1, with the potential, current and reference headroom kept) and whether it shows Display P3. CoreGraphics adds the physical size (`CGDisplayScreenSize`, from the EDID).
  - A notched display has two shapes, and both are in the list: the full panel (`nativeWidth` × `nativeHeight`, `fullRatio`, 3024×1964 and "1.54:1") and the area below the notch (`safeWidth` × `safeHeight`, `belowNotchRatio`, 3024×1890 and "16:10"). They're equal without a notch. The aspect ratio picker walks this list.
  - `ForkHwRules::checkStream()` (pure C++, `tests/fork/hwrules_test.cpp`) gives advisory warnings, which Settings shows under the resolution and FPS row (`ForkHardwareWarnings.qml`) and the stream profile dialog shows for the profile's values, falling back to the global ones. It warns about:
    - forced H.264 above 4096 pixels on a side (the hardware limit)
    - a forced codec without a hardware decoder
    - HDR without hardware HEVC Main10 or AV1, or with H.264 forced
    - a side above 8192
    - a frame rate more than 5 above the display's refresh rate
  - `ForkHwRules::ratioLabel()` names aspect ratios: the usual name within 1% (16:9, 16:10, 21:9, 32:9, 4:3, 3:2, 5:4, 1:1), else a reduced W:H up to 32:32, else a decimal like "1.54:1".
- **The Mac screen, described to the host** (`app/fork/clientdisplay.*`, `forklaunchargs.*`):
  - With anyosag/Apollo and its LuzVDA driver, the host's virtual display can describe the screen a stream shows on, so Windows picks a fitting scale and tone-maps HDR for this screen instead of a generic 32-inch, 3,800-nit one. Each launch and resume adds that screen's facts to the request:

    | Argument | Example | Meaning |
    |---|---|---|
    | `luzDisplay` | `1` | Version of these arguments |
    | `luzMm` | `302x196` | Physical size; left out when unknown |
    | `luzPanel`, `luzSafe` | `3024x1964`, `3024x1890` | The full panel and the area below the notch (the same without one) |
    | `luzHz` | `120` | Highest refresh rate; left out when unknown |
    | `luzGamut` | `p3` or `srgb` | |
    | `luzHdr` | `1600,1000,50` | Peak and full-screen nits, and black in 1/10000 nits; `unknown` for HDR of unknown brightness (the host picks), `none` without HDR |
    | `luzEdr` | `1600` | macOS's potential EDR headroom × 100, for the host's log |
    | `luzName` | `Built-in%20Liquid%20Retina%20XDR%20Display` | Percent-encoded, at most 63 bytes |

  - HDR brightness: Settings › "HDR peak brightness" if set; else a built-in panel with EDR headroom of 15.5 or more is taken to be a MacBook Pro's XDR panel (1,600 nits peak and 1,000 full-screen, from Apple's specifications; a 0.005-nit black, estimated); else unknown. The headroom threshold is a guess until checked on a MacBook: each launch logs `[fork] Describing <screen> to the host: …` with the size, shapes, refresh range, gamut, and the potential, current and reference EDR headroom.
  - `ForkLaunchArgs::capture()` reads the screen the stream opens on (`ForkVideoScaling::displayIndexFor()`) from `ClientHardware` on the main thread in `Session::initialize()`; `take()` hands the arguments to `startApp()` on the launch thread. They aren't sent to GeForce Experience. Other hosts ignore arguments they don't know, so they're sent to every other host rather than costing a request to check for Apollo first. The same goes for `luzTrackpad=mac`, which asks for Mac trackpad mode (see Trackpad passthrough) whatever this setting says.
  - Settings › "Describe this Mac's screen to Apollo hosts" (on by default) turns it off. "This Mac" shows each screen's size, gamut and the HDR peak hosts are told.
  - The arguments are pure C++ (`ClientDisplay::describe()`, `queryArgs()`), tested in `tests/fork/clientdisplay_test.cpp`.
- **Aspect ratios** (`app/fork/forkaspect.*`, `forkaspectratios.*`, `app/gui/ForkAspectRatioPicker.qml`, `ForkCustomResolutionDialog.qml`):
  - Apollo makes a virtual display at exactly the size a stream asks for, so any aspect ratio works. Settings › Basic Settings has an "Aspect ratio" dropdown above Resolution. Choosing a ratio refills the Resolution list with sizes of that ratio and selects the one that fills the display; the bitrate follows, as for any pick from the list. At startup the ratio of the saved size is selected (`AspectRatios.keyFor()`), and the saved size itself never changes. A size that isn't in the list stays as "Custom (W×H)".
  - The ratios, in order: the display's own shapes, then 16:10, 16:9, 21:9, 32:9, 4:3, 3:2, 5:4, 1:1 and "Custom ratio…" (a W:H field: `21:9`, `12:5`, `2.39:1`). A notched display has two shapes, offered separately: "Full display, with the notch area" (3024×1964, 1.54:1) and "Below the notch" (3024×1890, 16:10). Without a notch there's "Native (16:9)". A standard ratio that a shape already is (16:10 below the notch) isn't listed twice. With more than one display a "For display" box appears, built-in first.
  - The sizes (`ForkAspect::presetsFor()`, pure C++, `tests/fork/aspect_test.cpp`): the largest even size of the ratio that fits the display ("fills this display"), 720, 1080, 1440, 2160 and 2880 lines, and well-known monitor sizes within 1% of the ratio, like 2560×1080 and 3440×1440 (a well-known size replaces the generated one of its height, so 21:9 has no 3412×1440). Sizes above the display are kept and marked "larger than this display", since Apollo can render above the panel's resolution. Every side is even and within 256 to 8192.
  - The display a size is measured against (the box): the full panel for "Full display", the area below the notch for "Below the notch". For any other ratio on a notched display, the area below the notch while the stream goes there (the notch bar or Stretch is on, or upstream's choice for the window mode is a Space, which Borderless windowed is), else the full panel, the same decision `ForkPolicy::useSpacesFullscreen()` makes when the stream starts. The list refills when those settings change.
  - "Custom" in the resolution list opens `ForkCustomResolutionDialog` instead of upstream's dialog: width and height from 256 to 8192, "Keep aspect ratio" (the picker's ratio, or the starting size's), the typed size's ratio live ("3440 × 1440 · 21:9"), and a note when odd sizes will be rounded down to even. It has no GeForce Experience warning, since Apollo makes the display. The stream profile dialog's Resolution row offers the same ratios (an Aspect ratio row that isn't saved) and the same dialog as "Custom…"; profiles still store width and height.
  - `StreamProfiles::createSession()` rounds the session's width and height down to even and logs `[fork] Rounded the stream size WxH to W'xH'`. Apollo got odd sizes as typed, while moonlight-common-c only rounds the height, and only after the launch request.
- **Native macOS look** (`app/gui/Fork*.qml`, `app/fork/windowchrome.*`, `app/fork/mac/windowchrome_mac.mm`):
  - The app uses Qt's native `macOS` style, so controls follow the system appearance and accent color. `main.cpp` still picks Material elsewhere, but the QML look changes aren't gated, since LuzLunar is macOS-only.
  - On macOS 15 and later the main window gets a real `NSToolbar` (Liquid Glass buttons on macOS 26) with SF Symbols. `ForkNativeToolbar.qml` mirrors main.qml's toolbar buttons into it and clicks the QML button when a native one is clicked, so upstream's behavior and shortcuts stay. While the native toolbar is active, the QML toolbar is clipped to zero height but stays in the focus chain. Keyboard and gamepad navigation still reach its buttons (Up from a grid's top row, Tab on Settings), and the native item of the focused button is highlighted: prominent on macOS 26, selected before. The delegate builds a new `NSToolbarItem` each time AppKit asks, from per-item state.
  - The window stays opaque, as in the design: the title bar and native toolbar sit on the Night or Day toolbar color above a hairline, and the page is drawn in `ForkTheme.bg`.
  - Rounded tiles with hover, press and focus states; dialogs are rounded panels with a shadow.
  - Menus and combo box lists open inside the main window (`Popup.Item`), because gamepad navigation sends its keys to the main window.
  - Spinners use `ForkBusyIndicator`, which has a fixed size. The style's spinner is an animated WebP, so builds need the `qtimageformats` plugin (CI installs it).
  - SF Symbols in QML come from an image provider (`image://sfsymbol/<name>`, `app/fork/sfsymbols.*`, `app/fork/mac/sfsymbolprovider.mm`), because Qt Quick's `icon.name` can't reach them. Elsewhere `SfSymbols.available` is false and the SVGs stay.
  - The app icon is an Icon Composer icon (`scripts/fork/LuzLunar.icon`: the "moon path" mark, a gold crescent over its reflection on water drawn as broken lines, on Night navy), which macOS 26 renders in Liquid Glass. `build-mac.sh` compiles it with `actool` into `Assets.car` plus a flattened `LuzLunar.icns` for older macOS.
  - CI saves screenshots of the main views in light and dark (`app/fork/screenshotharness.cpp`, the `LuzLunar-screenshots-*` artifact).
